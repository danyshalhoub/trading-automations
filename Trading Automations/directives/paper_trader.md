# Directive: Live Paper Trader

## Objective
Run a roster of strategies live against real daily price data on Alpaca **paper** trading only, keep an honest record of how they actually perform, and re-test/refresh that roster whenever Dany chooses to rerun the tournament — there is no passive weekly automation. If a week goes by without a rerun, the roster simply stays as-is; that's a deliberate choice ("keep the same 4"), not a failure state.

## Tools
- Script: `paper_trader/strategies_lib.py` — shared indicator engine (RSI, MACD, Bollinger, MA crosses, gaps, volume, seasonality, relative strength, etc.). Every strategy is a "spec" — `{name, indicator_type, params, hold_days}` — evaluated through this same fixed, vetted code, whether backtesting or trading live. `indicator_type` must be one of the registered types; `params`/`hold_days` are clamped to hard-coded safe bounds (`clamp_params`, `clamp_hold_days`) before ever being backtested or traded, regardless of where the spec came from.
- Script: `paper_trader/active_strategies.json` — the current live roster (4 strategy specs). `trader.py` reads this every day; `weekly_tournament.py` rewrites it whenever it's run.
- Skill: `.claude/skills/stock-thesis-generator/` — run this in a Claude Code session to generate 20 new candidate strategy *parameterizations* as structured JSON (indicator_type + params + a plain-English thesis) — never code — written to `paper_trader/weekly_candidates.json`. Replaces the old `thesis_generator.py` script, which called the Anthropic API directly (paid, and required a passive GitHub Actions secret Dany never set up); this does the same reasoning for free, on demand, in-session.
- Script: `paper_trader/weekly_tournament.py` — the re-tournament, run manually whenever Dany decides to: downloads price data through *today* (a rolling window, not a fixed range — this is what makes "rerun" actually mean something), loads `weekly_candidates.json` if present (produced by the skill above; absent file just means "re-test the 4 incumbents only, no new candidates"), backtests incumbents + any candidates together, applies the train/test cheat-check (train ≤ 2021-12-31, test > 2021-12-31 through today), ranks cheat-check survivors by test-half P&L, and takes the top 4. If fewer than 4 survive, keeps incumbents (in their prior order) in the remaining slots rather than shrinking the roster. Writes the new roster to `active_strategies.json`, appends full results to `thesis_history.jsonl`, writes `weekly_tournament_report.md`, and deletes `weekly_candidates.json` so it can't be silently reused next time.
- Script: `paper_trader/trader.py` — scans `strategies_lib.ALL_TICKERS` for whatever's in `active_strategies.json`, enters/exits positions on each strategy's `hold_days` timer, appends every closed trade to `paper_trader/trade_log.csv`.
  - **Order handling is submit-then-confirm-next-run (rewritten 2026-08-05), not submit-and-assume (the original design).** The daily workflow runs at 5:30 PM ET, after market close, so a DAY order it submits cannot fill until the next session opens — hours after the job has already exited. A run can never learn its own orders' outcome synchronously. So: new entries get submitted and recorded in `paper_trader/pending_entries.json` (keyed by Alpaca order ID), not written into `positions.json` until a *later* run confirms the fill; exits get submitted and the position gets a `pending_exit_order_id` field but stays in `positions.json` until a later run confirms the sell filled. Every run's first step is reconciling whatever the previous run left pending, using the order's real status and fill price from Alpaca (`get_order_by_id`) — not an approximated `yfinance` close. A pending order that comes back expired/canceled/rejected: a failed entry is just dropped (never became a position, free to signal again later); a failed exit clears the pending flag so that same run's normal exit scan retries it (its hold period has already passed, so it's already due).
  - **Why this changed:** the original version treated "no exception on `submit_order()`" as proof the trade happened, and immediately logged it to `trade_log.csv` / removed it from `positions.json` on that basis. On 2026-07-14, the exit order for `ACN_rsi_oversold` (entry 2026-06-29, 80 shares) was submitted and accepted, but never actually filled (it expired) — Alpaca still held the shares, but the code logged a fake closed trade (`+$785.60`, using a `yfinance` close as a stand-in exit price since it never checked the real fill) and dropped the position from tracking. The shares sat as a real, live, completely untracked position for three weeks until Dany noticed ACN on the Alpaca dashboard and it got traced back (2026-08-05). Fixed by: removing the fabricated row from `trade_log.csv` (all-time realized P&L corrected from $9,647.13 to **$8,861.53**, 38 trades to **37**), restoring `ACN_rsi_oversold` to `positions.json` with its real entry price ($123.80, from Alpaca's own avg-entry — its blended cost basis across two same-day ACN buys under different strategies, since Alpaca tracks positions per-symbol, not per-strategy) and its original overdue `exit_date` so the now-fixed exit logic retries the sale on the next run, and the reconciliation rewrite above so this class of bug can't recur.
- Script: `paper_trader/performance_report.py` — reads `trade_log.csv`, writes `paper_trader/performance_report.md` (win rate, total trades, per-trade % gain, per-strategy breakdown), and emails a weekly digest. The report and email both show two sections: "This Week" (trades with `exit_date` in the last 7 days) and "All-Time" (cumulative since inception) — don't conflate the two when reading the Total P&L figure (fixed 2026-07-26 after the cumulative total was mistakenly sent as if it were the week's P&L).
  - Both sections also show a **vs S&P 500** line (added 2026-08-04): for each closed trade, it looks up SPY's price on that trade's own `entry_date` and `exit_date` (via `yfinance`, same `lib.BENCHMARK` = "SPY" already used elsewhere) and computes what the same `POSITION_SIZE` would have earned in SPY over that exact window, then rolls those up the same way real trades are rolled up. This is a trade-by-trade benchmark (matched entry/exit windows), not a calendar buy-and-hold comparison — it isolates strategy skill from market beta since every trade is compared to SPY over its own holding period rather than an arbitrary shared window. If SPY data can't be fetched (no network, Yahoo Finance hiccup), the vs-S&P line is silently omitted and the rest of the report/email still sends normally — this is a soft-fail by design, not an error to chase.
  - An **Open Positions** section (added 2026-08-04) now appears at the top of both the report and email, reading `positions.json` directly — ticker, strategy, entry date, exit date, and days until close (soonest-to-close first). This covers *unrealized* positions, which is otherwise invisible: everything else in this report/email (win rate, P&L, vs-S&P) is realized-only, sourced from `trade_log.csv`, which only gets a row once `trader.py` actually closes a position.
- Script: `paper_trader/reconcile_positions.py` — read-only audit, added 2026-08-05 after the ACN incident. Compares `positions.json`'s tracked share counts per ticker against Alpaca's real, live positions (`client.get_all_positions()`). Flags both directions of drift: Alpaca holding a ticker/quantity `positions.json` doesn't know about (an orphaned exit, ACN's failure mode) and `positions.json` believing more is open than Alpaca actually shows (a phantom entry that was logged as bought but never filled — the same bug, mirrored onto the buy side). Never places, cancels, or modifies any order, and never writes to `positions.json`/`trade_log.csv` — any mismatch it finds needs the same by-hand reconciliation ACN got (confirm the real qty/avg-entry on the Alpaca dashboard, then correct the tracking files to match). The 2026-08-05 rewrite of `trader.py`'s order handling prevents *new* instances of this bug going forward, but doesn't retroactively re-check any of the trades already logged before that fix — this script is the way to check for other pre-existing instances. Run manually, any time: `python reconcile_positions.py` (needs `ALPACA_API_KEY`/`ALPACA_SECRET_KEY` in the environment, same as `trader.py`).
- Script: `paper_trader/notify_failure.py` — emails an alert if any workflow step fails (auth expired, rate-limited, unhandled exception). Shared by both workflows via the `WORKFLOW_NAME` env var. Only runs on failure.
- Workflow: `.github/workflows/daily_trader.yml` — runs `trader.py` + `performance_report.py` after US market close on weekdays, commits `positions.json`, `pending_entries.json`, `trade_log.csv`, and `performance_report.md` back to the repo. The push step retries with a fetch+rebase (up to 5x) instead of giving up on the first rejection (added 2026-08-05) — a plain failed push here would silently discard that run's real, already-executed order results, since the runner is torn down right after.
- Workflow: `.github/workflows/weekly_tournament.yml` — **manual-only** (`workflow_dispatch`, no cron schedule). Trigger it from the GitHub Actions tab (or just run `weekly_tournament.py` locally with Claude Code) whenever the tournament should rerun; auto-commits the new `active_strategies.json` + `thesis_history.jsonl` + report straight to `main` when it runs. No human review step on the commit by design (paper trading only, no real money at risk) — see Safety Rules.

## Expected Outputs
- `positions.json` — currently open (confirmed-filled) positions. A position mid-exit carries a `pending_exit_order_id` field until the sale is confirmed on a later run — still counts as open until then.
- `pending_entries.json` — entry orders submitted but not yet confirmed filled, keyed by Alpaca order ID. Reconciled (and cleared) at the start of the next run; never read by `performance_report.py`, so a newly-submitted entry doesn't show as an open position until the run after it actually fills.
- `trade_log.csv` — one row per closed trade (ticker, strategy, entry/exit date, entry/exit price, shares, % gain, $ P&L). This is the source of truth for live performance — never delete rows from it, with one documented exception: the fabricated `ACN_rsi_oversold` row removed 2026-08-05 (see `trader.py` entry above) because it didn't represent a real trade at all, not because it was an ordinary mistake in a real one.
- `performance_report.md` — regenerated every run; summary stats + full trade table.
- `active_strategies.json` — the current live roster of exactly 4 strategy specs; rewritten every Friday.
- `thesis_history.jsonl` — one JSON line per week: every candidate evaluated that week (new + incumbent), its full backtest stats, cheat-check verdict, and which 4 made the next roster. Append-only audit trail — never delete rows from it.
- `weekly_tournament_report.md` — human-readable summary of the latest weekly run.
- A weekly email (Fridays, via `performance_report.py` which still runs on the daily schedule) to `GMAIL_ADDRESS` summarizing open positions (with days until close), win rate, trade count, P&L, and the vs-S&P-500 comparison. The open-positions list still sends even if no trades have closed yet — only the win-rate/P&L/vs-S&P stats are skipped in that case. Unrelated to the (now manual-only) tournament rerun — this keeps running regardless of whether the roster was refreshed that week.
- A failure-alert email to `GMAIL_ADDRESS` any day either workflow errors out (no silent failures — if you don't hear from it and don't get an alert, check the Actions tab manually).

## Key Settings
- `active_strategies.json` — the live roster; each spec's `hold_days` and `params` are the per-strategy exit timer / thresholds.
- `POSITION_SIZE` (top of `trader.py` and `strategies_lib.py`) — flat dollar amount per trade.
- `strategies_lib.PARAM_BOUNDS` / `HOLD_DAYS_BOUNDS` — the hard safety clamps every strategy spec passes through before it can be backtested or traded, regardless of source.
- `weekly_tournament.TRAIN_CUTOFF` / `MIN_TRADES_TO_SURVIVE` / `ROSTER_SIZE` — cheat-check split date, minimum trade count to be statistically meaningful, and roster size (currently 4).
- Required secrets (GitHub Actions repo secrets, or local `.env` — see `.env.example`): `ALPACA_API_KEY`, `ALPACA_SECRET_KEY`, `GMAIL_ADDRESS`, `GMAIL_APP_PASSWORD` (a Gmail *app password*, not the real password). No Anthropic API key is needed anywhere in this pipeline anymore.

## How the Roster Changes Over Time
This went through three phases: (1) fully manual — re-run tournament scripts by hand, eyeball `performance_report.md`, hand-edit `trader.py`'s strategy list; (2) fully passive — `weekly_tournament.yml` auto-ran every Friday and called the Anthropic API directly via `thesis_generator.py`; (3, current) **manual, by design** — Dany never set up billing for the passive API call, and decided passive automation wasn't the right model anyway. Now:
  - To rerun the tournament: type `/run-tournament` in a Claude Code session in this repo — it chains the `stock-thesis-generator` skill, `weekly_tournament.py`, a plain-English results summary, and a prompt before pushing. (Or do the steps manually: run the skill to write `weekly_candidates.json`, then run `weekly_tournament.py`.) You can also trigger `weekly_tournament.yml` manually from the GitHub Actions tab (with `weekly_candidates.json` pre-committed, or without it to just re-test incumbents).
  - To skip a week: do nothing. `active_strategies.json` isn't touched by anything except `weekly_tournament.py`, so the same 4 strategies keep trading via `trader.py` until the next manual rerun. This is a valid, intentional choice, not a degraded state.
  - A candidate's `indicator_type` + tunable params always come from the fixed registry in `strategies_lib.py`; nothing (Claude in a session, or a hand-authored spec) ever writes or influences execution code, so a bad or adversarial candidate can't produce out-of-range behavior — every param is re-clamped before use regardless of source. To retire an indicator type entirely (not just let it lose a given tournament), remove it from `strategies_lib.DIRECTIONS`/`PARAM_BOUNDS` — that requires a human edit and a normal commit, same as any other code change.

## Safety Rules
- `paper=True` must never be removed from `make_client()` in `trader.py`.
- Never hardcode `ALPACA_API_KEY`/`ALPACA_SECRET_KEY`/`GMAIL_APP_PASSWORD` — always read from environment/secrets.
- `trade_log.csv` and `thesis_history.jsonl` are append-only records — trading logic should only ever add rows, never rewrite or delete history. The one exception on record (2026-08-05, the fabricated ACN row) was a manual, human-approved correction of a row that never should have existed, not a precedent for casually editing history — treat any future case the same way: flag it, don't silently rewrite.
- Candidate strategies — whether hand-authored or proposed by Claude in a session via the `stock-thesis-generator` skill — never come with executable code, only structured `{indicator_type, params, hold_days, thesis}` that `strategies_lib.py` clamps to fixed bounds and evaluates through hand-written, human-reviewed indicator formulas. This is why auto-commit to `main` is acceptable when `weekly_tournament.yml` is triggered, despite no human review step on that commit: the blast radius of a bad proposal is bounded by the clamps and the fixed indicator set, and it's paper money regardless.
- If you ever add real-money trading, revisit the "no human review" decision above — it was made specifically because this is paper-only.
